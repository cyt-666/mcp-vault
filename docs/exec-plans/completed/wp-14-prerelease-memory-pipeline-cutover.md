# WP-14 Prerelease Memory Pipeline Cutover

Status: Complete
Owner: Codex
Created: 2026-08-26
Last updated: 2026-08-26

## Purpose and user-visible result

MCP Vault is still prerelease. When the memory architecture changes, persisted
work from the replaced architecture will not be interpreted by the new Worker
or migrated into the new semantic model. Upgrade to this generation will:

1. permanently discard every old `memory.*` job row;
2. clear every old memory projection, raw input, proposal, candidate,
   diagnostic, idempotency result, and derived memory vector;
3. delete old managed memory Markdown through Vault Core while retaining its
   revision/history and ordinary backups;
4. create only current-generation memory jobs with an explicit generation
   marker; and
5. admit one fresh full-Vault Phase 1 extraction with no inherited cursor.

The user's ordinary Vault notes and attachments remain untouched. Provider,
model, extraction-policy, credential, audit, non-memory job, revision, and
backup state remain intact.

## Current repository state

- Old and new extraction jobs share the durable type `memory.extract`.
  `WorkerSupervisor` dispatches by `job_type` only, so a pre-redesign row can be
  reclaimed by the current Phase 1 handler and resume its old
  `last_completed_path` cursor.
- Current extraction output records carry
  `EXTRACTION_PIPELINE_VERSION = 8`, but durable job payloads do not carry or
  enforce a memory-pipeline generation.
- Migration `0010` introduced Stage 1 and consolidation tables without
  invalidating preexisting memory jobs. The former legacy reset attempted to
  preserve explicit memories and could incorrectly treat any active extraction
  singleton as the fresh regeneration job.
- `memory.reset_legacy` removes selected legacy records through Vault Core but
  intentionally leaves current two-phase records intact. That behavior no
  longer matches the prerelease cutover decision.

## Scope and non-scope

### Included

- Forward migration `0011` that removes all old memory jobs and all database
  memory state while preserving non-memory operational/canonical state.
- A current memory-pipeline generation constant added to every newly admitted
  memory job.
- Worker admission that terminally cancels a `memory.*` job whose payload is
  missing or carries another generation, before invoking its handler.
- A Vault-scoped persistent `memory.reset_pipeline` job that idempotently
  deletes the old managed memory namespace through Vault Core, purges any
  residual database state, writes empty current artifacts, records cutover
  completion, and admits a fresh Phase 1 job.
- Admin labels/readiness/progress and operator documentation for the clean
  cutover rather than legacy compatibility.
- Migration, crash-recovery, Vault-isolation, handler-version, and frontend
  tests.

### Not included

- Preserving or semantically converting any memory generated by a replaced
  prerelease pipeline.
- Deleting ordinary notes, attachments, their revision history, provider
  configuration, credentials, audit records, backups, or non-memory jobs.
- A user-selectable production data migration policy. A future stable release
  must make compatibility and export decisions explicitly in a new ADR.

## Invariants and risks

- SQL migration may delete memory database rows because they are replaced
  prerelease state, but managed Markdown deletion still goes through Vault
  Core and creates normal history/outbox evidence.
- Every query and cleanup remains scoped by `VaultContext`, except migration
  `0011`, which deliberately applies the same cutover to every Vault in the
  installation before workers start.
- A crash during managed-file cleanup leaves the reset job/state incomplete;
  restart retries the idempotent cleanup and never resumes an old extraction
  cursor.
- Only a current-generation, full-scope, fresh extraction job may clear the
  durable regeneration-pending marker.
- Old memory tasks restored from a snapshot or otherwise reintroduced are
  cancelled before a Provider call, preventing accidental billing.
- Deleting old memory Markdown is intentionally destructive in the current
  Vault view, but revision history and existing backups remain recoverable.

## Proposed design

### Migration boundary

`0011_prerelease_memory_pipeline_cutover.sql` deletes all `jobs` rows whose
type begins `memory.`, all memory FTS/projection/raw/proposal/candidate/
diagnostic/idempotency rows, and `embedding_records` whose object type is
`memory` (vectors cascade). It recreates empty consolidation state with clear
`pipeline_generation` and `regeneration_pending` fields and adds a partial
unique index for one active `memory.reset_pipeline` job per Vault.

The migration cannot mutate the filesystem. On every affected Vault, startup
therefore admits a durable reset job because no current generation is recorded.

### Job generation gate

`MEMORY_PIPELINE_GENERATION` is distinct from the Stage 1 prompt/fingerprint
version. Every `memory.extract`, `memory.consolidate`, `memory.revalidate`,
`memory.rebuild`, and `memory.reset_pipeline` payload includes it. The Worker
checks this marker before handler lookup/execution and cancels mismatches with a
redacted lifecycle log. This is a hard boundary, not a fallback parser.

### Reset and fresh regeneration

The reset handler holds the Vault memory write lock while it:

1. enumerates managed files below `_mcp-vault/memory/`;
2. deletes each current file through Vault Core;
3. transactionally purges residual Vault-scoped memory state;
4. writes empty `MEMORY.md`, `memory_summary.md`, and `raw_memories.md` for the
   current architecture; and
5. records the current pipeline generation with regeneration pending.

The handler then admits a current-generation `memory.extract` job with
`scope=all`, `include_evaluated=false`, `fresh_start=true`, and a new job ID.
It clears `regeneration_pending` only after confirming that exact payload. If
AI configuration is not ready, the reset completes with the pending marker;
startup/periodic reconciliation admits the fresh job later.

## Decisions

- Use an explicit destructive cutover instead of attempting to infer whether
  an old payload is semantically compatible.
- Keep note content and its normal revisions canonical; only the managed memory
  namespace and memory operational/derived state are reset.
- Keep extraction fingerprint/prompt versions separate from the larger memory
  architecture generation.
- Do not retain old memory job history in this prerelease cutover; those rows
  are misleading and can be retried accidentally.

## Surprises and discoveries

- The old job visible in deployment (`01a037dc…93630e`) was not merely labelled
  incorrectly: the new handler was actively consuming its old cursor because
  the durable row type had not changed.
- The old singleton admission bug could clear the regeneration marker for an
  unrelated extraction, making `legacy_reset_version = 1` insufficient proof
  that every note had current Phase 1 coverage.
- A newly initialized empty Vault must not wait for an upgrade reset. First-
  Admin setup now records the current generation directly; only Vaults that
  existed before migration 0011 receive `memory.reset_pipeline`.
- File-event memory work must remain suppressed until the required fresh job is
  durably admitted. The outbox still schedules ordinary indexing during this
  window, but no extraction/revalidation/rebuild memory job can race cleanup.

## Rollback and recovery

Migration 0011 is forward-only and intentionally destructive for prerelease
memory state. Rollback means restoring a pre-upgrade service backup and its
matching binary. Existing Vault revision history/backups can recover deleted
managed memory Markdown, but the new binary will cut it over again. A crash
during reset is recovered by the durable singleton job; current-generation
completion is recorded only after file and database cleanup succeed.

## Outcomes

Migration 0011 now removes every replaced prerelease memory task and database
row while preserving ordinary Vault and non-memory operational state. Managed
memory Markdown is cleared idempotently through Vault Core by
`memory.reset_pipeline`; current generation state is recorded only after
cleanup succeeds. Every new memory task carries `pipeline_generation`, and the
Worker cancels missing/mismatched tasks before their handlers or Providers run.
The required Phase 1 regeneration is a new `fresh_start` job with no inherited
progress cursor; file events and external remember/manual work cannot race the
pending cutover. Admin and documentation now describe discard-and-regenerate,
not compatibility migration.
